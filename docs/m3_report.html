Milestone 3: Progress Report

When Does Executing Contract Rules Help? LLM Resolution of Real Kalshi Markets

Team: Abhinav Sivakumar (as21153), Devansh Vikram (dv2482), Pranjal Mishra (pm4084)

Code: https://github.com/pmxlr8/kalshi-rules

Response to the Milestone 2 feedback

We got two main comments. The first was to focus on when and why structured execution helps, instead of trying to show that C4 beats the other methods. The second was that our evaluation data was artificial, so good results on it would not say much about real prediction markets. We changed the project around both points. We dropped the edited contracts and now evaluate only on real settled Kalshi markets, with the evidence source that the rules point to and Kalshi's actual outcome as the label. Instead of one overall number per method, we break the results down by model size and by properties of each item (how close the value is to the threshold, whether the evidence contains a number that would flip the answer, whether the rule has one or two bounds), and we check which step of the pipeline each error comes from.

1. System implemented so far

Data. We pulled 113,152 settled markets from 21 series through Kalshi's public API (closed between 2026-09-11 and 2026-11-16). Each market has its rules text, the outcome, a structured threshold and the final value. Applying the threshold to the final value gives back Kalshi's outcome on 113,094 of the 113,095 markets with a numeric value, so we get exact labels without any hand annotation. The one mismatch is a Nasdaq-100 market whose threshold field says 26,990 while the rules text says "above 26,989.99"; the rules text decided it.

Evidence. For weather markets we use the NWS daily climate report for the station named in the rules, which is the source Kalshi settles on. It matches Kalshi's value on 366 of 367 station-days. The report also lists the record, the normal, the departure from normal, last year's value and the other daily extreme, so the model has to pick the right number; on 56% of weather items at least one of these would flip the answer. We also built a version with both the preliminary and the final report. For finance and economics the evidence is currently one line with the official value.

Study set. 666 markets from 100 events (384 weather, 144 finance, 138 economics), split by event into a dev set of 162 items (25 events) and a test set of 504 items (75 events). We only change prompts based on dev.

Methods. All methods use the same model, evidence and temperature 0. B1 sees the contract but no evidence. C1 answers directly. C2 uses chain of thought. C3 writes a JSON spec of the rule, extracts the value and applies the spec in text. C4 does the same spec and extraction, but Python applies the spec. O1 and O2 are C4 with the gold spec or the gold value plugged in, to locate errors. We run three models through the Groq API: ALLaM 2 7B, Qwen 3.8 27B (reasoning off) and gpt-oss 20B (low reasoning). Llama 3.1, which we planned to use in Milestone 2, is no longer available on Groq, so ALLaM is our small model.

Scoring. We report two scores. Strict scoring requires the exact output format. Tolerant scoring re-reads the same saved outputs and only fixes formatting problems, such as a verdict written as a sentence instead of JSON or bounds put in the wrong field. It makes no new model calls, so the gap between the two scores shows how many errors are about formatting rather than reasoning. Intervals come from a paired bootstrap over events. All model calls are cached, a self-test checks the labels and parsers, and a small Streamlit demo runs C2 and C4 side by side on any market.

2. Baseline results

Without evidence (B1), Qwen 27B gets a balanced accuracy of 0.50 on 96 dev items, which is chance. So the outcome cannot be guessed from the contract alone, and the model does not seem to know these outcomes. The direct answer (C1) is our main baseline. On dev it gets 100.0% with Qwen 27B (162 of 162), 77.2% with ALLaM 7B and 96.4% with gpt-oss 20B given both reports.

The main pattern is that structure only helps when the direct answer is weak. With Qwen 27B the direct answer is already right on every dev item, so there is nothing for C4 to improve. With ALLaM 7B, C4 is 19.1 points better than C1 under tolerant scoring (95% CI 9.5 to 30.4), and the gap is largest on weather items, items near the threshold and items where a distractor would flip the answer (Figure 1B). Under strict scoring it reverses: C4 is 16.0 points worse than C1 (95% CI −29.9 to −3.3), because the small model often breaks the JSON format in one of C4's two steps.

4. Experiments and comparisons completed

We ran the baselines B1 and C1, and C1 and C4 on all dev items for ALLaM 7B and Qwen 27B (Qwen's C4 run is still going). C2 has run on part of dev. gpt-oss 20B was run on the weather dev items with both reports. We also compared two versions of the spec format on a 12-item pilot. For every run we compute strict and tolerant scores, accuracy by item type, and paired differences with event-level bootstrap intervals.

5. What worked

  • Using real markets. The labels come straight from Kalshi, and the data has plenty of hard cases: 51 of 162 dev items are within one step of the threshold and 43 have a distractor that would flip the answer.
  • C4 with the small model, once formatting is handled.
  • Tolerant scoring, which turned out to be a simple way to separate formatting errors from reasoning errors.

6. What failed

  • Strict C4 on ALLaM 7B is worse than the direct answer (56.8% against 72.8%).
  • With both reports (about 3,300 input tokens, close to its 4,096-token limit), ALLaM 7B started repeating itself or printing blank lines and gave no valid answer on 7 of 7 items, so we stopped that run.
  • Qwen 27B is already at 100% on dev, so it cannot show any benefit from structure on these markets.
  • We hit the daily token limits of Groq's free tier, so C2, the oracle runs and the test set are not finished.

7. Failure analysis and likely causes

ALLaM 7B, direct answers. 37 of 162 answers are wrong, and 34 of those say YES when the answer is NO. It answers YES 48.8% of the time while the true rate is 29.6%. Of the 30 wrong weather answers, 18 give only a verdict without a value, 7 cite the wrong value, and 5 cite the right value but compare it wrongly at a boundary (for example, it said 70 is not in "69° to 70°"). C4 gets 34 of these 37 right, which points to the comparison step, the part that C4 hands to Python.

ALLaM 7B, C4 under strict scoring. All 70 errors are on weather. In 34 cases the extractor found the right value, but our prompt asked it to copy the source line word for word, and the report's fixed-width lines contain long runs of spaces, so it ran out of tokens before closing the JSON. In 30 cases it put both bounds of a "between" rule into the threshold field. Only 6 are real value errors, and all of them are other numbers from the report: last year's value (2), the normal (2), another number (2).

gpt-oss 20B with both reports. C1 abstains on 3 of 84 items, two of them on the only dev day where the preliminary and final reports disagree (NYC low, 58 against 54). C4 picks a wrong value 3 times, and each time it is the record high, which sits right next to the observed value in the report.

Revisions. The two reports differ on only 6 of 84 dev weather items and change the outcome on 2 (12 and 2 of 300 on test). Real revisions are much rarer than in the edited set we planned in Milestone 2.

8. Changes attempted and their effects

  • Spec format. In our first version, one-sided rules could put the threshold in "low" or "high", and C4 got only 4 of 12 pilot items right. After switching to a single "threshold" field it got 12 of 12. Tolerant scoring of the old outputs also gives 12 of 12, so all 8 errors were formatting. C3, which applies the same spec in text, got 12 of 12 even with the old format.
  • B1 prompt. The first version allowed the model to abstain, and it did on 10 of 12 items. We now force a YES or NO, so B1 is a real chance baseline.
  • Output limit. ALLaM 7B writes some text before its JSON and was getting cut off at 60 tokens. We raised the limit to 320, and strict invalid answers are now 8 of 162.
  • Parser fix. Our parser for the report numbers missed times like "11:12 AM" and read only 144 of 384 reports. After the fix it reads all 384, and the dev items with a flipping distractor went from 15 to 43.
  • Rate limits. Each model has its own daily limit on Groq's free tier, so we run one queue per model and let it wait when it hits the limit.

9. Remaining gaps relative to our success criteria

Our Milestone 2 primary metric was C4 minus C2 on the edited contracts, which we dropped. The new main result will be C4 minus C1 and C4 minus C2 broken down by model and item type on the test set, which we have not run yet. We also still need C2 on all of dev, C3, the compute-matched C2-SC baseline, B2, the oracle runs and the spec-agreement uncertainty measure (H3). Finance and economics evidence is only one line, so those domains test reading the rule but not finding the value. Our largest model is 27B, and we no longer compare against KalshiBench because we stopped using web search evidence.
